# 01 — Prerequisites & Input Context Checklist

Before conducting a machine learning code analysis and generating the technical report, the analyst (or AI agent) must ensure that the necessary project materials are present in the workspace.

Lacking these files leads to conceptual misunderstandings, hallucinated metrics, or incorrect architectural assumptions.

---

## The 5 Essential Pillars of Analysis Input

### 1. Complete Executable Source Code
* **What to provide:**
  - All primary Python scripts (`.py`), orchestration modules, and utility files.
  - Jupyter Notebooks (`.ipynb`) in sequential order if the pipeline was built in notebooks (e.g., `01_prepro.ipynb`, `02_model.ipynb`, `03_eval.ipynb`).
  - Configuration files (`config.yaml`, `.env.example`, constants definitions).
* **Why it is critical:**
  - The analysis requires exact line-by-line inspection. Every code block presented in the report must feature exact line numbers (e.g., `model.py line 45–62`) and match the actual source files character-by-character.
* **Risk if missing:**
  - Fabricated functions, incorrect variable names, and code block parity failures.

---

### 2. Dataset Samples, Schemas & Dictionaries
* **What to provide:**
  - The dataset files (Excel `.xlsx`, `.csv`, `.parquet`, `.json`, SQLite/PostgreSQL schema dumps).
  - If the dataset is large or confidential, provide:
    1. A sample extract containing 50–100 representative rows.
    2. Column schema definitions (column name, data type, unit of measurement, nullability).
    3. Target class distribution or value ranges (e.g., Min, Max, Mean, Standard Deviation).
* **Why it is critical:**
  - Understanding input space dimensionality, search space combinatorial size (e.g., $N_1 \times N_2 \dots$), normalization boundaries, and missing value strategies.
* **Risk if missing:**
  - Wrong assumptions about feature distributions, misleading evaluations, and inability to calculate real numbers during step-by-step simulation.

---

### 3. Execution Logs & Experiment Traces
* **What to provide:**
  - Actual terminal output logs (`run_log.txt`, stdout/stderr recordings).
  - Training progression logs (epoch-by-epoch loss, validation accuracy, convergence history).
  - Optimizer iteration logs (e.g., PSO fitness per 50 iterations, early stopping trigger points).
  - Random seed information used during runs.
* **Why it is critical:**
  - The report must document empirical behavior rather than theoretical assumptions.
  - Demonstrates whether the algorithm reached local optima, suffered from gradient vanishing, or achieved `inf` fitness due to reward function design.
* **Risk if missing:**
  - Artificial or speculative claims about convergence speed, execution runtime, and model stability.

---

### 4. Domain Context & Mathematical Formulation
* **What to provide:**
  - Objective function definitions (Loss formula, Fitness function, Multi-objective weights).
  - Domain constraints and rules:
    - In dietary/nutrition recommendation: Harris-Benedict / Broca formulas, macronutrient ratios (e.g., 25% Breakfast, 10% Snack, 30% Lunch), glycemic indices.
    - In NLP/Fact-checking: NLI label taxonomy (Entailment, Contradiction, Neutral), retrieval threshold ($\text{cosine similarity} \ge 0.75$).
    - In financial/industrial ML: Risk penalties, latency budgets, regulatory thresholds.
* **Why it is critical:**
  - Standard ML metrics (such as raw F1-score or RMSE) can be completely misleading if not contextualized within the domain rules.
* **Risk if missing:**
  - Evaluating an optimization algorithm as if it were a text classifier, or evaluating an imbalanced retrieval task with raw accuracy.

---

### 5. Output Artifacts & Generated Files
* **What to provide:**
  - Output files generated by the code (e.g., `hasil_rekomendasi.xlsx`, prediction CSVs, generated plots).
  - Saved model weights metadata or checkpoint metrics.
* **Why it is critical:**
  - Used to produce visual evidence tables, screenshot figures, and verify that the code's export routine works as intended without data loss.

---

## Input Validation Matrix

| Category | Minimum Acceptable Input | Optimal Input |
|---|---|---|
| **Code** | Python files with all dependencies importable | Tested repository with virtual environment |
| **Data** | Sample rows + data dictionary | Complete dataset or representative validation split |
| **Runtime** | Single run console log | Multiple run logs with diverse seeds and profiles |
| **Domain** | Written problem statement & objective formula | Official guidelines, paper references, benchmark standards |
| **Outputs** | One final generated artifact | Artifacts across baseline and edge cases |
